# Framework_WWJ 代码、注释与分区规范

> 适用范围：Framework_WWJ 自有 Runtime、Editor、Tests 和 Samples 代码。

## 1. 总体原则

- 优先让读者一遍看懂所有权、状态变化和调用顺序。
- 一个类型只承担一个清晰层次的职责，避免巨型 Loader、Manager 和 Utils。
- 公共 API 保持小而稳定；只因当前阶段的真实用例增加能力。
- 先保证正确的生命周期与清理，再考虑编辑器便利性和扩展点。

## 2. 命名与成员

- 类型、方法、属性使用 PascalCase；局部变量和参数使用 camelCase。
- 私有字段使用 `m_` 前缀，例如 `m_runtimeModules`。
- 静态私有字段使用 `s_` 前缀；常量使用 PascalCase。
- 序列化字段优先使用 `private` + `[SerializeField]`，不要为了 Inspector 暴露公共可写字段。
- 布尔名称表达状态或能力，如 `IsLoaded`、`CanTick`，避免含义模糊的 `flag`、`status`。
- 接口和抽象类型名称表达能力或角色，不保留旧框架的拼写错误以换取不存在的兼容性。

## 3. 中文注释

- 公共类型、接口、属性和公开方法使用中文 XML 注释，说明“为什么存在、谁调用、生命周期约束和失败行为”。
- 生命周期入口、克隆/销毁、排序、回滚和场景切换等关键流程使用中文行内注释解释原因。
- 不逐行翻译明显代码，例如不要给 `count++` 添加“数量加一”。
- 注释必须随行为更新；过期注释比没有注释更危险。
- 专有名词可保留英文，如 Runtime、Handler、Tick、SO，并在首次出现时解释语义。

## 4. `#region` 分块

按类型实际内容选择以下顺序，不存在的分区不创建：

```csharp
#region Inspector 配置
#endregion

#region 运行时状态
#endregion

#region 公共属性
#endregion

#region Unity 生命周期
#endregion

#region 框架生命周期
#endregion

#region 公开 API
#endregion

#region 内部实现
#endregion

#region 调试与验证
#endregion
```

- 不使用多层嵌套 region 隐藏过长类型；类型过长时优先拆职责。
- region 名称使用简洁中文，确保折叠后仍能理解类的结构。
- 接口很短时无需为了形式强行分区。

## 5. 方法与控制流

- 方法保持单一目标；名称应说明动作和对象。
- 优先使用早返回减少嵌套，但不要把一个完整生命周期切成大量难以追踪的小方法。
- 排序、注册、加载、卸载和销毁分别由命名明确的方法负责。
- 不在属性 getter 中触发克隆、加载、场景创建等重大隐藏副作用。
- 对顺序敏感的集合使用稳定、可预测的算法，并在注释中说明相同优先级规则。

## 6. 必要保护而非过度保护

必须验证：

- Inspector/配置资产传入的外部引用；
- 公共 API 参数；
- 生命周期状态转换；
- 重复模块、缺失依赖和克隆失败；
- Unity 对象已销毁但托管引用仍存在的边界；
- 场景卸载和应用退出的清理入口。

避免：

- 在调用链每一层重复同一个 null 检查；
- 捕获异常后无记录地吞掉；
- 用大量布尔标记修补不清晰的状态机；
- 为没有需求的线程安全、热插拔或容错分支提前设计；
- 失败后假装成功或悄悄创建隐式默认模块。

内部不变量由构造/注册流程保证后，可以使用清晰的错误或断言暴露编程错误，不需要层层降级。

## 7. SO 与运行时状态

- 原始 Module SO 资产只保存设计时配置，不写入 Play Mode 状态。
- 运行时字段必须位于克隆体、Handler 或 Runtime 容器中，并明确其所有者。
- 销毁克隆体前先完成模块卸载和 Handler 清理。
- 不依赖 Unity 编辑器自动恢复资产来掩盖运行时污染。
- Odin 特性用于改善分组、校验和多态配置，不把展示特性散落成业务逻辑。

## 8. 日志与异常

- 日志包含模块身份、作用域、生命周期阶段和原始异常。
- 配置错误尽量在 Editor 校验和启动校验阶段暴露。
- 无法继续保证框架状态时明确失败；能够安全继续清理时，记录错误后继续卸载其余模块。
- 第一版不建立复杂日志抽象，除非阶段设计证明需要替换日志后端。

## 9. 文件与依赖

- 一个主要公开类型一个文件，文件名与类型名一致。
- Runtime 不引用 UnityEditor；Editor 和 Tests 通过独立 asmdef 依赖 Runtime。
- 核心不直接引用可选业务模块。
- 第三方依赖放在明确适配层，避免渗入所有模块契约。

## 10. 评审检查

- [ ] 类型职责能否用一句话说明？
- [ ] 创建者、持有者、调用者和销毁者是否清楚？
- [ ] 中文注释是否解释关键原因和约束？
- [ ] region 是否帮助阅读，而不是隐藏臃肿？
- [ ] 是否存在重复保护、静默失败或隐藏副作用？
- [ ] SO 原资产是否保持纯配置？
- [ ] 卸载和异常路径是否与成功路径同样清楚？
