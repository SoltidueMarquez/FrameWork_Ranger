# Framework_WWJ 全量重建基线

> 状态：等待参考项目与第一个可验证游戏目标。  
> 本文定义“从零开始”时的工作边界，不提前锁死最终架构。

## 1. 本次重建的起点

本轮先做两件事：

1. 把旧项目事实、旧架构和历代计划归档到 `Docs`；
2. 清除 `Assets/Plugins/Framework_WWJ/Main` 与 `Utils` 中的旧实现，避免新架构继续被旧类型和序列化资产牵引。

第三方插件不在清理范围。Packages、ProjectSettings 和其他用户改动不在本轮修改范围。

## 2. 设计前必须获得的信息

收到参考项目后，先输出对比报告，不立即搬代码：

- 每个参考项目解决了什么真实问题；
- 模块、配置、场景、异步和全局状态分别如何建模；
- 哪些能力是项目规模带来的必要复杂度，哪些只是历史负担；
- 可复用的是概念、API、实现还是仅测试用例；
- 依赖许可、Unity 版本和第三方包是否兼容。

同时明确第一个游戏目标的：

- 核心循环；
- 场景数量与切换方式；
- 数据量、资源类型与平台；
- 必需模块；
- 可量化验收标准。

## 3. 暂定设计原则

以下原则来自旧项目经验，但仍可被参考项目分析推翻：

- 先做最小闭环，再扩展能力。
- 核心只定义稳定生命周期和模块所有权，不提前放入业务功能。
- Runtime、Editor、Tests 使用清晰的程序集边界。
- 全局与场景对象的创建者、持有者、销毁者必须明确。
- 初始化失败不能被静默吞掉；错误策略和回滚策略要可观察。
- 不因“未来可能需要”加入热更、动态模块、递归配置包或大型工具库。
- 每个基础模块先写行为契约和测试，再写编辑器体验。
- ScriptableObject 用于资产化配置还是运行模块，需要用实际场景验证后决定。

## 4. 建议阶段

### Phase 0：参考分析与架构决策

- 导入/阅读参考项目；
- 确定新框架最小术语、目录和程序集；
- 写架构决策记录（ADR）；
- 定义第一个垂直切片游戏目标；
- 形成不超过一页的 V1 核心契约。

### Phase 1：基础骨架

- Runtime/Core asmdef；
- 最小模块契约；
- Entry/Runtime 的所有权和生命周期；
- global/scene 合并规则（若最终采用）；
- 初始化顺序、失败行为和逆序退出；
- 一个无业务测试模块；
- EditMode 测试与最小 PlayMode 场景。

### Phase 2：基础模块

只实现游戏目标马上需要的模块。候选通常是：

- 日志/诊断；
- 时间与 Tick；
- 场景流程；
- 资源访问；
- 对象池；
- 音频。

候选不是固定清单，不能一次性全部开工。

### Phase 3：游戏垂直切片

用框架完成一个小而完整的游戏目标，记录真实摩擦点。框架 API 的扩展必须由垂直切片需求驱动。

### Phase 4：硬化与工具

- 性能与内存基准；
- Domain Reload/Enter Play Mode 配置验证；
- 场景切换和异常恢复；
- Inspector、创建菜单和诊断窗口；
- 包结构、示例和使用文档。

## 5. Phase 1 进入编码前的决策清单

- [ ] 模块实例的载体：普通 C# / SO / MonoBehaviour / 组合方案
- [ ] 配置与运行时状态是否分离
- [ ] global 与 scene 的精确定义
- [ ] 重复模块的判定维度：key / 类型 / 接口 / 实例
- [ ] 生命周期是否需要异步，以及取消模型
- [ ] Tick 是默认能力还是显式 opt-in
- [ ] 模块依赖如何声明与校验
- [ ] 模块访问方式
- [ ] 错误、日志与诊断策略
- [ ] Runtime/Editor/Test asmdef 与第三方依赖边界
- [ ] 第一个游戏目标的验收测试

在这些问题没有足够证据前，不创建 `V2` 目录，也不把旧类型重新复制回来。
