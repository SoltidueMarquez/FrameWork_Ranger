## 1. 本轮设计目标

从框架骨架开始，优先设计两个相互配合的部分：

1. 模块基类、模块接口以及模块自身的生命周期能力；
2. 配置、实例化、驱动和清理这些模块的框架运行时骨架。

正式计划必须让实现者可以直接按图和逐脚本规格编码，不把关键结构选择留到实现阶段。

## 2. 用户已明确的方向

### 2.1 Odin + ScriptableObject 配置

- 默认沿用 HTY 的 Odin + ScriptableObject 配置体验。
- 每个模块以 SO 资产作为配置入口和运行时模板。
- 框架启动或作用域加载时克隆模块 SO，所有运行状态只写入运行时克隆体。
- 作用域结束时卸载模块并销毁克隆体，不能污染或修改原始配置资产。

这是下一轮设计的默认方向。若分析发现 Unity 生命周期、测试或所有权存在明显问题，应先向用户说明再提出调整，不得静默替换为其他载体。

### 2.2 模块生命周期与顺序

- 每个模块必须参与统一的加载、运行和卸载流程。
- 每个模块需要表达自身的加载/卸载顺序需求。
- 加载失败、部分加载、卸载顺序和重复模块等精确语义仍待确认。
- 下一轮需要决定“独立加载/卸载优先级”还是“加载排序 + 默认反序卸载”。

### 2.3 全局与场景模块

- 框架必须能配置始终加载、跨场景存在的全局模块。
- 框架必须能配置只在特定场景或场景作用域中存在的模块。
- 场景切换时哪些模块复用、重建或覆盖，以及全局/场景重复模块的处理规则仍待确认。

### 2.4 Module + Handler

- 用户倾向让框架支持 Module + Handler 的逻辑拆分，以便多态扩展和替换实现。
- Module 可承担框架身份、配置入口和公开门面；Handler 可承载实际逻辑。
- 是否每个模块强制拥有 Handler、Handler 如何由 Odin 序列化、框架运行时自身是否也采用相同拆分，均需下一轮详细设计。

## 3. 正式计划的强制交付形式

下一轮计划必须同时提供：

- 代码逻辑层次结构图，展示入口、配置、运行时、模块、Handler 与作用域之间的所有权和调用关系；
- 建议的实际目录树；
- 按层次划分的完整脚本清单；
- 每个脚本的文件路径、类型、继承/接口关系、序列化字段、运行时字段、属性、公开方法、内部方法和实现方式；
- 初始化、Tick、场景切换和卸载时序；
- 错误与边界行为；
- EditMode、PlayMode 和最小示例的验收计划。

详细格式见[计划交付规范](./02_Core_Skeleton_Plan_Output_Spec.md)。

## 4. 未来代码风格约束

- 以可读性和可维护性优先，不为了“万一”加入层层重复保护。
- 对真正的公共边界、Unity 引用和生命周期状态做必要验证；内部已由结构保证的条件不反复检查。
- 使用清晰、详细的中文 XML 注释和关键流程注释，让框架学习者能理解设计原因。
- 使用有意义的 `#region` 划分字段、属性、生命周期、公开 API 和内部实现。
- 方法保持职责单一，命名表达意图，避免巨型 Loader、巨型 Utils 和隐藏副作用。

完整要求见[代码规范](../../04_Standards/Code_Style_And_Comments.md)。

## 5. 当时没有决定的内容（已在第一阶段关闭）

- 模块基类、Handler 基类和生命周期接口的具体名称；
- 同步或异步加载，以及取消模型；
- 模块 key、类型、接口或上下文访问方式；
- 配置资产的数量、继承层次和合并规则；
- 全局运行时由谁启动、场景运行时如何挂接；
- Tick、Pause/Resume、动态 Add/Remove 是否进入第一版；
- 模块依赖声明和循环依赖处理；
- 核心 asmdef、Editor asmdef 和 Tests asmdef 的最终目录与依赖；
- 第一批基础模块和最小验证游戏目标。

这些问题必须通过下一轮对话确认，而不是由实现者自行猜测。
