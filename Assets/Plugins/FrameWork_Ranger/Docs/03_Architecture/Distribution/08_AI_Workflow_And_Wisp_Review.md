# WispFramework 参考与 AI 工作流替代方案

> 补充于 2026-09-11 准备任务。状态：可行性评估与推荐，尚未实施工作流，也不代表用户已经决定取消 App。参考程序内部的指令、模板与命令仅作为资料读取。

## 1. 结论

AI 可以在具备代码访问、GitHub 权限和验证环境时，把游戏开发中产生的通用框架修改迁回源仓库，完成代码调整、测试、提交和推送。对当前以开发者本人使用为主的场景，建议先验证 **AI + 模块清单 + 少量可重复执行脚本**，暂缓完整桌面 App。

可以省去自建界面、桌面打包、窗口状态、App 自动更新等工作；模块身份、依赖、版本锁、文件归属、更新基线和验证仍然需要有明确实现。AI 能调用现有 Git/Unity 工具并编排步骤，关键文件操作应逐步固化，避免每次临时生成一套同步语义。

这修订的是此前的技术推荐优先级，不改变用户的目标：按需导入、各模块独立更新、游戏内开发并回流框架。原 App 文档仍可作为未来界面的需求来源。

## 3. AI 可以做到什么，需要什么条件

| 工作 | AI 能承担的部分 | 必要条件 |
| --- | --- | --- |
| 新项目按需导入 | 读模块清单、解析依赖、执行导入和验证 | 模块边界可用，源版本明确，GUID 保留 |
| 游戏内修复框架 | 理解调用场景、修改源码、补充合适验证 | 可访问游戏上下文和实际依赖 |
| 回流框架源码 | 提炼通用改动、合并源分支、处理冲突、更新文档 | 能访问两端和安装基线；项目特化边界明确 |
| 更新 GitHub | 执行 Git 提交/推送，具备相应工具时创建 PR | 已认证且有相应权限，符合分支规则与用户授权 |
| 发布独立模块 | 更新版本与变更说明，调用既有发布流程 | 版本/依赖规则及发行物构建可重现 |
| 无人值守执行 | 可由非交互任务或自动化触发 | 另行设置触发器、运行环境、凭据和失败处理；普通对话不是常驻监视器 |

OpenAI 官方文档介绍了本地环境的提交、推送、PR 和工作树能力，也提供非交互模式支持脚本工作流。依据：[本地环境](https://learn.chatgpt.com/zh-Hans/docs/environments/local-environment)、[非交互模式](https://learn.chatgpt.com/zh-Hans/docs/non-interactive-mode)。这些是能力说明，不证明当前账户已经有目标 GitHub 仓库写权限。

本机只读检查确认系统 Git 和现有 `Tools/UnityCli.ps1` 可用；未在 PATH 中发现 `gh`。Git 推送本身不依赖 `gh`，PR/API 流程可在正式接入时选择 GitHub CLI 或可用连接工具。本轮没有测试远端认证、创建分支、提交或推送。

## 4. 建议的最小工作流

### 第一步：建立长期可读的项目关系

记录框架源仓库、游戏中框架目录、模块定义、已安装版本/提交、模块文件范围和配置排除规则。机器绝对路径放本机映射；游戏仓库保存可移植的来源和版本记录。

沿用项目现有 `AGENTS.md` 和任务记录；将回流步骤写成简短项目规则，成熟后再提取为 Skill。Skill 能封装说明、资料和可选脚本，但不代替版本锁或执行验证。依据：[AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)、[Build skills](https://learn.chatgpt.com/docs/build-skills)。

### 第二步：在游戏里完成修改与验证

例如用户提出“修复事件订阅释放问题，并将通用修复同步到框架仓库”。AI 在真实游戏场景修复后，区分框架改进与游戏规则、场景、配置。能从上下文明确判断的常规改动直接处理；会改变公共接口或框架定位的选择需要明确语义。

### 第三步：迁移通用改动到源仓库

使用安装基线、游戏当前内容、框架目标分支当前内容比较。源仓库已经发展时迁移修改意图，不能把游戏中较旧的整个模块覆盖回去。独立源工作区便于隔离其他未提交改动；新脚本和 `.meta` 一起处理，项目配置保持排除。

### 第四步：验证、提交与远端更新

复用现有 Unity CLI 入口进行导入/编译和真正受影响的测试。游戏里运行成功还需检查框架能否在没有游戏业务依赖时使用。只暂存此次通用修改；按已授权的分支策略提交/推送，协作时可走 PR。无需逐文件确认，但发布与合并策略应事先说清楚。

### 第五步：模块发布与其他项目更新

框架源码提交后，按模块版本规则生成发行物。游戏 A 可安装新版本，游戏 B 继续锁定旧版本。源分支已合入、模块已发布、游戏已升级是三个独立状态，AI 的结果报告应分别说明。

首次验证建议由用户主动触发一次完整任务。重复几次后，再决定是否增加定时扫描或事件触发；不要一开始每次保存脚本就自动推送远端。

## 5. 最少保留哪些工具

- 模块清单和安装来源记录：作为事实，不只依赖对话记忆。
- 导入/升级计划及受管理文件写入：首版只覆盖实际需要的模块和 Assets 模式。
- 基线比较与必要恢复能力：只处理本次受影响文件，不建立全工程快照系统。
- Git 和已有 Unity 验证命令：优先复用，频繁重复的步骤才封装脚本。

可以先把这些放在现有框架仓库的 Tools 和文档中，不必立即新建 App 仓库、通用 CLI 平台、MCP 服务或 Registry。若日后做界面，直接调用这些已验证的操作能力。

此前发现的 Resource/Pooling/UI Editor 交叉依赖仍须按实际安装组合整改。AI 能执行整改，但换成 AI 入口不会让当前模块天然独立，详见[模块拆分设计](./05_Modules_And_Sync_Design.md)。

## 6. 什么时候值得做 App

| 使用情况 | 更合适的路线 |
| --- | --- |
| 自己或少数开发者，日常已用 AI/Git | 优先 AI 工作流与轻量工具 |
| 很多重复安装操作，需要低延迟、离线固定步骤 | 提供直接脚本/命令入口；必要时加薄界面 |
| 面向其他团队、美术/策划或不用 AI 的用户 | App 的可发现性、统一状态和操作体验更有价值 |
| 模块目录庞大、多人管理大量项目，需要可视化浏览 | 再评估集成管理 App |

AI 工作流仍有模型用量、等待时间和偶发判断差异的成本，因此应让机械动作可重复执行、可独立验证。App 则增加 UI、安装包和升级维护成本。当前建议优先减少后一类投入，不宣称 AI 能永久替代所有管理产品需求。

## 7. 下一阶段验收建议

选一个真实游戏测试副本和 Core + 池基础层 + 引用池 + 事件中心，跑通：按需导入 → 游戏内通用修复 → 源分支回流 → 独立版本更新。增加上游并发修改、项目配置保留、`.meta` 连续性以及第二项目保持旧版四个检查点。

若这条链路顺畅且人工操作负担可接受，就可以继续使用无独立 App 的方案。当前完成的是可行性评估，尚未搭建或验收这条端到端链路；是否正式暂缓 App 由用户后续决定。
