# 新仓库筹备与开发路线

> 日期：2026-09-11。用户已表达后续新建 GitHub 仓库；本轮只准备方案，没有创建、提交或推送远程仓库。

## 1. 仓库职责建议

| 对象 | 建议职责 | 不放入的内容 |
| --- | --- | --- |
| 现有 `FrameWork_Ranger` 框架仓库 | 模块源码、Unity 测试/样例、模块定义、版本变更与发布构建入口 | App 安装包、用户游戏源码 |
| 新 App 仓库（候选名 `RangerHub`） | 桌面 UI、同步/安装领域逻辑、Git/Unity/文件适配、工具测试和 App 文档 | 参考 EXE/ASAR、真实游戏工程、用户凭据 |
| 每个游戏仓库 | 业务代码、项目自有配置、安装模块副本/包引用和项目锁记录 | App 本机缓存与恢复快照 |

“模块分别管理更新”不要求一模块一仓库。建议源码仍在同一框架仓库，模块独立定义与发布；减少跨仓库依赖变更和历史管理成本。是否公开 App/框架仓库分别决定，不能由参考程序的托管方式推导。

本轮文档暂存框架 Distribution 目录。新 App 仓库建立时迁入 App 需求/架构/路线文档，并在旧位置保留指向新权威位置的索引；框架内的模块整改和分发契约仍由框架仓库维护，避免两份文档各自变化。

## 2. 建议目录（尚未创建）

以 Electron/TS 候选为例：

```text
RangerHub/
  README.md
  AGENTS.md
  docs/
    product/             需求与用户旅程
    architecture/        来源、基线、计划、发布与 ADR
    references/          调研与官方资料索引
  apps/desktop/
    main/                桌面进程及操作调度
    preload/             有限 IPC 接口
    renderer/            项目、模块、回流工作区
  packages/
    domain/              模块、依赖、来源和基线模型
    application/         安装、升级、回流、发布用例
    infrastructure/      Git、文件、GitHub 与 Unity 适配
  tests/
    fixtures/            人工构造的模块与 Unity 资产样本
    integration/         临时目录、临时 Git 仓库与恢复测试
  .github/workflows/     实现阶段再加构建、测试与发布
```

目录表示职责，不要求开工就建所有包；简单原型可先在一个工程内按文件夹分层。若改选 Avalonia，保持领域/应用/基础设施分层，把 desktop 改为 .NET UI 工程即可，不维护两套核心同步实现。

新仓库初始化还需确定 README、许可证选择、忽略项、依赖锁、构建命令和发布方式。许可证未确定前不套用第三方参考的声明；不把本地二进制研究目录加入新仓库。

## 3. 分阶段交付

| 阶段 | 交付 | 完成标准 |
| --- | --- | --- |
| P0 准备（本轮） | 调研、需求、依赖盘点、技术候选、仓库路线 | 有事实来源、未决项和后续可执行任务 |
| P1 只读桌面原型 | 项目登记、源映射、模块目录、依赖诊断、差异与计划展示 | 不修改目标项目即可解释一次安装/更新会改什么 |
| P2 首批模块边界与安装 | 在框架仓库整改必要 Editor 边界；App 按白名单安装，保存来源与基线 | Core + 引用池 + 事件中心可在临时游戏使用，失败可恢复 |
| P3 开发回流闭环 | 模块差异选择、冲突、隔离源工作区、提交/显式推送 | 游戏内通用修复回到框架分支，不混入项目配置与业务资产 |
| P4 独立版本闭环 | 模块定义、独立发布、升级/回退、移除和第二项目验证 | 一个模块发布后项目 A 可升级，B 保持旧版；依赖与本地修改正确处理 |
| P5 扩展 | UI/资源后端组合、UPM 模式、自动更新、多平台 | 每项按真实使用场景单独验证 |

**P1–P4 共同构成满足当前目标的首版。** P1 不是完整产品；回流和独立版本不能无限延期。P2 的框架整改范围按实际阻塞最小化，不自动接管历史 Pooling 的全部未验收项。

## 4. 首批开发工作项

1. 确定产品名、仓库归属/可见性和桌面技术栈，在新仓库记录候选转正式的决定。
2. 制定最小模块定义与项目锁格式，用现有模块事实填真实样本；不伪造版本兼容区间。
3. 实现只读扫描与计划，并制作项目/模块/回流页面最小交互。
4. 检查 Core 配置初始化、Pooling Editor 与 Event 依赖闭包，在临时 Unity 工程做裁剪验证。
5. 在人工文件树上实现 B/L/T 比较、操作日志与写前复核，再接入真实项目安装。
6. 实现一次新增/修改/删除及 `.meta` 配对的回流，并在临时 Git 仓库验证精确暂存。
7. 接入模块标签/发布记录，让两个测试项目验证独立升级与版本锁。

不需要先建设账号系统、私有 Registry 或完整 CI 平台；等已有可验证构建和发布入口，再接入相应自动化。

## 5. 开工前待定项与建议默认值

| 议题 | 建议默认值 | 影响 |
| --- | --- | --- |
| App 名称与 GitHub 仓库名 | 工作名 Ranger Hub；候选仓库 RangerHub | 包身份、应用数据目录和发布地址 |
| 仓库所有者与可见性 | 使用用户指定账户；可见性等待明确 | 新建远程仓库时必须得到具体目标，当前不推定 |
| 支持平台 | Windows 首发，中文 UI | 打包、路径与交互测试范围 |
| 长期维护语言 | Electron/TypeScript 原型；如倾向统一 C# 则 Avalonia | 工程工具链与 UI 实现 |
| 首版安装形态 | Assets 管理副本 | 最大限度保留现有框架路径和游戏内可编辑体验 |
| 第一批模块 | Core + 池基础层 + 引用池 + 事件中心 | 边界整改和端到端验收范围 |
| 远程模块分发 | 源仓库标签/发布记录，逐步接 GitHub Releases | 无需先运营 Registry；私有下载认证需验证 |

这些问题不阻塞本轮文档准备。正式开工时先处理影响创建仓库和构建的选项，其余按已记录方案推进。参考代码和旧探索文档不自动把候选方案变成用户决定。

## 6. 本轮完成与验证范围

已完成三个程序的静态研究、当前模块与 Editor 依赖盘点、首版需求、资产归属和三方同步设计、官方资料核对，以及独立仓库路线。文档交付前检查 Markdown 本地链接、任务 JSON、新增 Unity 文档 `.meta` 和 Git 差异。

没有启动参考 GUI 或测试联网行为，没有实现或运行 App，没有改框架 C# / asmdef /配置资产，没有跑 Unity 编译测试。下一步从 P1 开始，P0 的技术建议仍可根据用户偏好调整。
