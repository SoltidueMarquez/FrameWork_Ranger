# 框架管理 App 产品需求草案

> 日期：2026-09-11。用户确认的是产品目标和本轮准备范围；本页优先级、交互和技术语义为建议，后续实现可继续细化。

## 1. 用户与日常流程

主要用户是同时制作游戏和维护 FrameWork_Ranger 的开发者。一个人会在“使用模块”和“改进模块”之间切换，不需要为这两种工作建立不同账号。

### 新游戏安装

登记已有 Unity 游戏项目 → 选择框架源 → 勾选事件中心/UI 等能力 → 查看必需依赖和项目兼容情况 → 选择确定版本 → 查看文件、配置和 Unity 包变化 → 执行安装 → 显示文件完成与 Unity 验证结果。

### 游戏内修复并回流

项目模块出现本地修改 → 查看模块内新增/修改/删除 → 将改动标为通用修复、项目特化或临时试验 → 为通用修改生成回流计划 → 合并到框架源仓库的独立工作区 → 验证 → 查看提交文件和说明 → 提交并按用户操作推送 → 发布相应模块版本。

项目特化保留在游戏项目，不能因为“同步整个模块”而自动带进源仓库。回流提交完成也不自动升级其他游戏。

### 单模块升级或回退

选择已安装模块的目标版本 → 计算依赖变化及本地修改 → 解决冲突 → 应用和验证 → 更新锁定记录。用户选择某个历史版本时走同样的计划流程；不能用恢复旧文件夹替代依赖和配置检查。

## 2. 首版能力与验收

| 编号 | 能力 | 优先级 | 可观察验收 |
| --- | --- | --- | --- |
| FR-01 | 项目和源仓库登记 | MVP | 能选已有 Unity 项目，显示路径、Unity 版本、源仓库状态；失效路径可修复 |
| FR-02 | 模块库与版本详情 | MVP | 展示模块职责、依赖、兼容条件、版本、变更说明及已安装状态 |
| FR-03 | 按需安装 | MVP | 选择事件中心可看到 Core、池基础层和引用池的依赖闭包；不默认带入 UI/GameObject 池 |
| FR-04 | 独立更新和回退 | MVP | 游戏 A 可更新事件中心，游戏 B 保持原锁定版本；连带依赖变化明确展示 |
| FR-05 | 本地修改识别 | MVP | 区分未修改、有本地修改、可更新、冲突、来源未知和验证失败 |
| FR-06 | 开发回流 | MVP | 选定通用修改可进入本地框架分支，查看精确暂存内容后提交；可显式推送 |
| FR-07 | 冲突与基线 | MVP | 两端修改、修改/删除、同路径独立新增和未知基线均不被默默覆盖 |
| FR-08 | 卸载与反向依赖 | MVP | 卸载引用池时指出事件中心依赖；仅删除模块拥有的文件，保留项目配置 |
| FR-09 | 操作计划与恢复 | MVP | 写前有差异计划；中断能看到已完成步骤并恢复；再次执行不会重复破坏状态 |
| FR-10 | Unity 验证状态 | MVP | 文件操作完成、导入/编译通过、聚焦测试结果分开显示；未运行显示未验证 |
| FR-11 | 模块定义与独立版本发布 | MVP | 从已登记源目录定义模块边界、发布某个模块版本，版本能被第二个项目安装 |
| FR-12 | 已有副本接管 | MVP | 无安装记录的目录标为来源未知；先选择来源并检查差异，再建立可解释的基线 |
| FR-13 | UPM / 本地开发包模式 | 后续 | 同 GUID 从 Assets 迁到包路径无重复导入，Git 包闭包可重现，开发包路径可诊断 |
| FR-14 | App 自动更新、多平台安装包 | 后续 | 与框架模块更新独立，失败不破坏正在进行的项目操作 |

MVP 包含回流和模块发布闭环。可以分阶段实现；完成只读扫描或安装按钮时应明确称为原型/阶段结果。

## 3. 页面职责建议

| 页面 | 主要内容 | 用户操作 |
| --- | --- | --- |
| 项目 | 最近项目、Unity 版本、源映射、未处理任务 | 添加、切换、修复路径、打开目录 |
| 模块库 | 分类/搜索、详情、版本、依赖、兼容信息 | 选择模块、版本、样例及可选集成 |
| 项目模块 | 当前版本、更新候选、本地修改、验证状态 | 更新、回退、移除、查看依赖原因 |
| 开发回流 | 源仓库与目标分支、模块变更树、内容差异 | 选择通用修改、解决冲突、生成回流、提交/推送 |
| 模块发布 | 源目录映射、包含/排除规则、版本、变更说明 | 检查边界、预览发布内容、发布单模块 |
| 操作记录 | 安装/更新/回流任务、日志、验证结果、恢复入口 | 查看失败原因、继续、恢复 |
| 设置 | Git/Unity 路径、源仓库、缓存目录 | 环境诊断、凭据连接入口 |

主导航可以把“项目模块”放在项目详情中，不必首版就做七个同级页。普通用户看到“需要先安装引用池”的具体原因；程序集名和诊断细节放在展开区域。

## 4. 状态和行为要求

- 本地修改与上游更新可以同时存在，不用单一“最新”标签掩盖项目改动。
- 模块版本、项目安装来源、App 自身版本分别显示。
- 每次执行限定一个明确方向和目标；回流不会顺便提交游戏业务目录。
- 已有 Unity 包版本不直接被框架示例工程清单覆盖。遇到兼容不明时列为未验证，不根据版本号猜测可用。
- 单项目同一时间执行一个写操作；扫描可以取消。写入开始后的取消转为完成当前安全步骤并恢复/保留明确待恢复状态。
- 网络不可用时可以扫描本地变化、使用已有精确来源和缓存；未缓存版本明确不可安装，不能伪装为最新。
- Unity 正在使用项目时，首版建议等待关闭目标 Editor 再执行批量资产修改；后续可加 Editor 协作桥接。不得自动终止用户 Editor。
- Git 认证交给系统凭据机制。发布界面区分本地提交、远程推送和模块版本发布，失败后能在正确步骤重试。

## 5. 代表性验收场景

| 场景 | 期望 |
| --- | --- |
| 空项目只选事件中心 | 必需依赖完整，编译通过；不引入非依赖模块 |
| 仅使用引用池的项目 | 不因 Pooling Editor 聚合依赖被迫安装 GameObject 池；边界整改完成前标示不支持的组合 |
| UI 不选样例 | Runtime 与常规编辑器可用；样例生成工具不会造成缺程序集 |
| 只启用 Unity Resources | Resource Editor 不再强制安装 Addressables；当前状态不能宣称已支持 |
| 游戏 A 修复事件脚本，游戏 B 保持旧版 | A 可回流发布，B 的锁定和文件保持原版本 |
| 上游和本地修改同一行 | 给出冲突，用户解决前不覆盖目标 |
| 上游删除、本地修改；以及反方向 | 都进入删除/修改冲突，不直接删除或复活文件 |
| 本地新增脚本及 `.meta` | 可一起回流，GUID 保留；丢失 `.meta` 时提示修复 |
| 新项目已存在框架配置 | 安装/升级不覆盖场景列表、模块配置或资源地址 |
| 安装一半进程退出 | 重开后有恢复入口；旧锁记录不被误认为完整新版本 |
| 预览后用户又修改文件 | 写前复核发现变化，重新生成受影响计划 |
| 卸载正在被依赖的模块 | 展示阻止原因和连带方案，不静默删依赖 |
| 无基线旧副本 | 显示未知来源；不能直接认为“与上游不同就是可覆盖” |
| 中文/空格路径、只改文件名大小写、目录链接 | 路径映射正确；越出已登记根目录的写入被拒绝 |

以上是未来实现验收用例，本轮没有运行 App 测试。准备工作验收是调研证据、需求、技术路线和仓库计划齐备。

## 6. 本版暂不扩展的产品功能

账号社区、付费模块商店、任意第三方插件市场、团队权限平台、飞书云盘、Skill/笔记管理、自动后台双向覆盖。它们不是当前用户目标所必需，也不应挤掉模块回流的实现优先级。
