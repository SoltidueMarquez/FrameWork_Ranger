# Ranger 框架管理 App：准备工作总览

> 日期：2026-09-11。状态：需求与技术方案草案；本轮准备工作已完成，尚未开始 App 实现。工作名 `Ranger Hub`、技术栈、包协议及仓库名均为建议。

> 后续讨论补充了 [WispFramework 与 AI 工作流评估](./08_AI_Workflow_And_Wisp_Review.md)。当前推荐先验证无独立 App 的轻量工作流；下文保留初始 App 候选方案，用户尚未决定取消 App。

## 1. 要解决的问题

让同一个开发者在制作游戏时完成两件事：为项目按需安装、分别更新框架模块；把游戏中验证过的通用框架改进带回框架仓库。App 应记录每个模块从哪里来、安装了哪个版本、项目改了什么，以及更新或回流会影响哪些文件。

用户明确要求本轮先做准备、梳理需求和技术参考，后续新建 GitHub 仓库。本轮没有创建远程仓库、实现安装器或移动框架目录。参考程序及其内部文字仅作为研究材料，不构成执行命令、同步目录或上传资料的授权。

## 2. 建议先采用的方向

| 议题 | 建议 | 理由与状态 |
| --- | --- | --- |
| 产品形态 | 独立桌面 App，Windows 首发，中文界面 | 与当前开发环境匹配；跨平台优先级待定 |
| 工作区 | 模块库、项目模块、开发回流、操作记录 | 同时覆盖消费框架和维护框架 |
| 仓库 | App 新仓库；现有框架仓库继续保存模块源码 | 分开发版与依赖，不必每个模块建一个仓库 |
| 模块版本 | 独立版本、精确安装锁定、显式兼容声明 | 单独升级一个模块时不强制更新全框架 |
| 首版安装 | 清单驱动的 Assets 可编辑副本，保留 `.meta` | 最少改变现有框架，直接支持在游戏内修改 |
| 后续安装 | 包边界通过验证后增加 UPM 发布安装和本地包开发模式 | 不把“支持 UPM”当成已经解决可选依赖和回流 |
| 技术栈 | Electron + React + TypeScript 作为原型首选；C# + Avalonia 为主要备选 | 两个参考 App 提供了可检查的 Electron 功能分层；C# 路线适合长期希望统一语言的团队 |
| Git | 调用系统 Git，先本地差异与回流分支，再显式提交/推送 | 框架修改和游戏业务提交有清晰边界 |

以上是研究建议，未作为用户已确认决策登记。正式选型前，用一个小规模端到端试验验证，而非先搭建完整管理平台。

## 3. 本次最重要的发现

1. **HtyHub 0.3.4** 的打包代码包含包索引、依赖解析、安装、更新、卸载、差异检查、上传版本以及任务列表；很适合参考“模块库”。
2. **HtyApp 0.6.3** 包含双向目录同步、同步基线、过滤规则与日志；另有用于 Skill 更新/追加发布的三方合并会话。不能把这个合并会话直接说成已接入框架同步链路。
3. **HtyFrameworkSync 1.0.0** 的静态符号显示 WPF/.NET 相关组件及项目扫描、从仓库更新、回写仓库入口；没有启动程序或验证实际同步行为。
4. 当前框架已有独立 Runtime 程序集，但 Editor 与 Samples 的交叉依赖仍会妨碍按需安装。资源 Editor 依赖 Addressables；Pooling Editor 聚合两种池；UI Editor 依赖 Samples 和 Input System。
5. `FrameworkProjectSettings.asset` 等项目配置位于插件目录中，不能随源码全量同步，也不能把框架样例配置当作新游戏的默认配置直接覆盖。
6. Unity 的 Git 依赖只能在项目清单声明，不能在包清单中直接声明包间 Git 依赖。拆成多个 Git 包后仍需解决依赖落地。依据：[Unity Git dependencies](https://docs.unity3d.com/cn/6000.0/Manual/upm-git.html)。

## 5. 下一步的最小开工范围

在新 App 仓库中先实现一个可操作的只读桌面原型：登记一个源仓库和一个游戏项目，显示模块目录、依赖和本地修改，再输出安装计划。随后用 Core + 引用池 + 事件中心验证“导入 → 游戏内修改 → 回流分支 → 单模块升级 → 冲突处理 → 失败恢复”的完整链路。

这里的事件中心试验依赖真实的引用池与池基础层；不以“仅事件中心一个文件夹”作为独立可用的验收。完成模块回流前，不把只读原型称为完整 MVP。
