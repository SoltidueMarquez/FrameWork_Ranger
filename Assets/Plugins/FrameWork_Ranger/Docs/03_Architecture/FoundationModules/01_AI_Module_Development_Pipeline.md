# FrameWork_Ranger AI 模块开发流水线

> 更新：2026-09-05，按已授权的工作流优化生效。
> 入口：项目根 AGENTS.md → `$work-with-framework-ranger` → `$build-framework-ranger-module`。
> 用户直接描述需求即可；涉及核心契约时再加载 `$framework-ranger-lightweight-refactor`。

## 1. 首轮：理解目标并保存输入

先从本次工作目录确定工程，读取 Docs 入口与[任务记忆协议](../../05_Skills/01_Task_Memory_And_Recovery.md)，查看相关模块事实和 Git 改动。不要因为个人 Skill 中的旧路径切换工程。

新模块、多轮需求或跨会话功能直接创建/恢复 `.workflow/<task-id>/requirements.json` 与 `progress.json`，先保存初始要求。普通解释与小修复按需处理，不机械建立全套文档。

判断用户本轮范围：讨论、设计、实施或修复。收到清晰的实施请求后持续推进；只要求研究或设计时保留该边界。现有授权和已确认回答持续有效，不要求用户重复描述或输入批准口令。

## 2. 问答：只解决影响结果的缺口

围绕实际需求整理：

- 要解决的问题、首批调用方与可观察结果；
- 必须支持、明确排除与可延后能力；
- Global/Scene 范围、所有权、获得与释放方式；
- 公共调用方式、必要的同步/异步、取消和失败语义；
- 直接依赖、真正需要的配置/Editor 支持；
- 如何用最小有效检查证明本次目标。

能从当前代码和用户已确认内容得到的答案直接记录。对会改变结果的未知选择给出推荐和影响；可以把相关问题一起问，不固定每轮问题数量。内部技术选择由 AI 在授权内决定，暂定假设单独标记。

关键回答及时写入 JSON，保留短原文与否定边界。不要等长任务结束或收到压缩提示才补记录。

## 3. 研究与可修改的设计

仅研究当前选择需要的资料。读取 LyingBottle/HTY 或 YokiFrame 时遵守该参考工程当前的入口和 Skills，保持只读；参考行为标记为事实、推断或候选，不自动成为项目决定。

不确定实现路线时，先做回答具体问题的小实验，再确定方案。设计至少说明公共行为、重要所有权/生命周期、依赖和目标路径。复杂关系用图，关键脚本说明职责和协作；无需先冻结所有私有字段、辅助方法或测试用例。

公共契约和范围变化说明影响，确认受影响选择即可。内部实现调整、代码组织优化及符合约定的缺陷修复直接推进，回写重要偏差。跨模块或核心契约变化仍用 ADR 记录当前决定及被替代决定。

## 4. 实施：一个可验收片段接着一个片段

沿用[模块交付契约](./02_Module_Delivery_Contract_And_Templates.md)的目录和依赖规则。工作项关联有效需求 ID；可按实际任务合并设计、实现与验证，不建立额外工作流引擎。

通常先把关键 API/算法与调用链做通，再接入 Module/Scope、必要配置和 Editor/示例。根据本次目标选择先后，不要求所有任务从空程序集开始。

保留 Runtime/Editor 依赖方向、SO 模板与运行状态分离、Unity GUID、用户改动以及必要的架构元数据。Handler、Provider、新测试程序集和编辑器页面按真实需求添加，不为形式完整创建空壳。

片段完成、关键发现、实际失败或启动较长命令时更新进度和下一步。新用户输入进入当前任务记录，不自动丢弃原目标。

## 5. 验证：与改动相称

使用 `Tools/UnityCli.ps1` 和[Unity CLI 开发规则](../../04_Standards/Unity_CLI_Development_Rules.md)。

- C# 改动实际编译。
- 复用能证明当前行为的聚焦测试或最小使用场景；有价值时再补回归用例。
- 生命周期、共享核心、资源后端或构建链路的变化，按受影响范围追加检查。
- 全框架回归、完整 Player 构建、性能/泄漏专项都需要具体理由，不是每个模块每次改动的固定门禁。
- 不默认使用 SHA-256、指纹、全环境快照、自动失效图、固定修复轮数或无差别重试。

存在真实错误就修复；环境阻塞只记录受影响工作，继续已有授权的独立工作。未运行的检查如实说明。代码生成完、编译过和行为验证通过是不同结果。

## 6. 恢复与收尾

恢复时按任务协议读取所有有效需求，包括已实现但仍需保持的要求；再读工作项、下一步和相关源码。不要重复调查完整工程或把历史方案重新当成待确认设计。

交付前逐条核对有效需求及关联结果。未完成要求保留为未完成，只有用户调整范围才能延期或放弃。更新受影响的模块 README、架构/ADR、实施说明、验收复盘和项目索引，不复制实时进度表。

本次范围完成后清空当前项与下一步。不会因为“下一模块已经排在计划里”就顺带开始它。

## 7. 事件中心试点

用户提出事件中心需求时，立即建立/恢复其任务记录并开始需求与设计。先查看实际 Reference Pool 契约；旧 Pooling 的验收待办继续如实保留，不把它们当成开始问答的前置条件。

实施 Event 时，只对实际依赖的 Reference Pool 行为补必要检查。若发现阻塞当前功能的依赖问题，说明范围并处理已授权的直接问题；不自动接管 GameObject、Addressables、Player 等无关验收。事件接口和订阅语义仍需按本轮需求确定，不从旧候选直接生成。

## 8. 典型自然语言输入

| 用户输入 | 应进入的行为 |
| --- | --- |
| “我想做一个事件中心，支持……” | 保存需求，查看相关项目事实，提出关键选择并推进设计 |
| “按刚才讨论的接口实现” | 恢复记录与已有授权，持续实现和必要验证 |
| “继续昨天的事件中心” | 匹配任务并恢复有效需求、进度与下一步 |
| “刚才那个行为改成……” | 保留历史，更新受影响要求和工作项 |
| “修一下 Inspector 的文字” | 做局部修改和适当检查，不启动完整模块建设 |
