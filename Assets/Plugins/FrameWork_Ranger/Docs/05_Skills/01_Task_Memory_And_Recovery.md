# JSON 任务记忆与恢复协议

> 生效：2026-09-05。适用于 FrameWork_Ranger 新模块、多轮需求和跨会话开发。
> 用户已授权按工作流优化文档更新 Skills 与流程。本页是实际操作规则，工具扩展仍按需决定。

## 1. 自动建立或恢复

用户自然描述需求后，先识别目标与工作范围。新模块、较复杂功能、需要多轮问答或预计跨上下文的任务，直接创建 `.workflow/<task-id>/requirements.json` 与 `progress.json`；不为创建这两份可逆的工作文件再次请求许可。

使用简短稳定的任务目录名，例如 `event-center`。从项目根目录的 [requirements 模板](../../../../../.workflow/_templates/requirements.json)和 [progress 模板](../../../../../.workflow/_templates/progress.json)复制，再填入本轮目标、有效要求和下一动作。模板不属于活动任务。

- 已有匹配目标的未完成任务：恢复其记录，并纳入本轮新输入。
- 用户明确重新设计或重新开始：可以建新目录并引用旧任务，保留仍有效的用户约束，标记被明确替代的决定；不删除历史或重复使用旧批准来授权新语义。
- 多个任务并存：按用户目标、任务 `goal` 和模块文档匹配，不仅按时间选最近任务。只有确实无法区分才简短询问。
- 只有解释、简单研究或小修复：不机械建立完整工作区；开始多轮关键问答时再记录。

第一次记录应在深入研究或第一轮关键提问之前完成，防止初始需求本身丢失。纯“帮我分析”保持分析范围；“请实现”在需求明确后继续实现，不强制再走一次批准仪式。

## 2. requirements.json 的最小内容

顶层字段使用模板即可，不需要新增 Schema 版本、哈希、签名或机器状态机。

| 字段 | 内容 |
| --- | --- |
| `task_id` / `goal` | 任务身份与用户想得到的结果 |
| `scope_notes` | 范围、非目标、用户偏好和已有授权依据，简短文字即可 |
| `questions` | 关键问题、回答短原文、整理含义、来源和关联需求 ID |
| `requirements` | 稳定 ID、当前要求、来源类别、有效状态及可观察验收 |
| `decisions` | 影响后续选择的决定、原因、来源及被替代内容 |
| `open_questions` | 真正未解决的问题及其影响，不记录已经得到答案的问题 |

单项需求形状：

```json
{
  "id": "REQ-001",
  "text": "填写本任务具体要求",
  "basis": "user_confirmed",
  "status": "active",
  "acceptance": "填写可以观察到的完成结果"
}
```

单项问答形状：

```json
{
  "id": "Q-001",
  "question": "实际问过的问题；用户主动提出时可注明议题整理",
  "answer_quote": "真实用户回答的短原文",
  "interpretation": "整理后的含义，保留否定条件和边界",
  "source": "对话位置或可定位资料，不虚构消息 ID",
  "requirement_ids": ["REQ-001"]
}
```

以上是填写说明，不是实际确认记录。`basis` 使用 `user_confirmed`、`project_fact` 或 `assumption`；AI 提出的推荐值不因落盘变成用户确认。`status` 使用 `proposed`、`active`、`superseded` 或 `deferred`。

**需求的有效性与完成状态分开。** 实现完成的需求继续保持 `active`，完成情况由工作项表示。新确认的附加约束直接加入有效需求集合，恢复时不能因它已经完成而漏读。

变更只改受影响内容：内部实现调整记一条必要说明；公共行为替换保留旧要求及替代关系。普通澄清不必独立建立 REQ 文件或重新批准整份规格。

## 3. progress.json 的最小内容

| 字段 | 内容 |
| --- | --- |
| `status` | `planning`、`in_progress`、`blocked`、`completed` 或 `cancelled` |
| `design_docs` | 当前需要的模块计划/架构/ADR 路径，均相对项目根 |
| `current_task` / `next_action` | 当前工作项及一条可以直接继续的动作 |
| `tasks` | 工作项、关联需求、状态、产物和真实结果 |
| `blockers` | 实际障碍、已尝试方法、需要什么条件；只影响相关工作 |
| `recent_notes` | 当前改到哪里、重要发现、运行中命令/日志位置，保持简短 |

单项工作形状：

```json
{
  "id": "WI-001",
  "title": "填写一个可验收片段",
  "requirement_ids": ["REQ-001"],
  "status": "pending",
  "outputs": [],
  "result": "",
  "verification": []
}
```

工作项状态用 `pending`、`in_progress`、`done`、`blocked`、`deferred` 即可。一个需求可以对应多个工作项。简单片段可在同一项中实现与验证，无需拆成多层依赖图。

`verification` 记录实际方法、结果和必要产物位置，可以是简短字符串或对象。源码检查、编译、测试、人工操作分别说清；未运行的检查不能写通过。变更确实影响旧结论时，将受影响工作项改回待处理，并说明原因，无需指纹系统。

## 4. 保存与恢复

保存时机：关键用户回答或纠正后、工作片段完成时、重要决定/失败时、启动长命令之前，以及切换阶段或结束当前对话前。一般问答可小批量保存。长时间连续工作约 20–30 分钟可补一个简短检查点；不依赖“即将压缩”的提醒，也不要求后台定时器。

新会话或上下文恢复后：

1. 读取本任务两份 JSON，包括所有 `active` 要求和仍会影响本次工作的决定。
2. 看 `current_task`、`next_action`、阻塞与最近记录。
3. 只打开当前动作相关的设计、源码、日志；记录有执行中命令时先查看状态，避免重复启动。
4. 核对明显现场差异，纳入用户新输入后直接继续；不重新扫全项目或重问已回答问题。

用户最新明确指令优先。记录与源码冲突时，区分“尚未实现要求”和“记录已过期”，局部修正，不把实现现状自动当成用户的新意图。

JSON 保存协作记忆，不会让已经停止的 AI 自动继续运行；无需为了使用该协议先建设监督服务。

## 5. 收尾与记录体量

交付前逐条核对 `active` 要求都有对应结果；没有完成的保持待办或阻塞。延期、放弃或改变范围须有用户依据，不能靠修改状态把遗漏消掉。工作项按本次范围完成后，任务设为 `completed`，清空 `current_task` 与 `next_action`。

Markdown 保留稳定架构、计划解释和交付结果，JSON 保存当前要求与进度；引用路径，避免复制整份设计或同时维护两套实时状态表。历史问答过长时可另存归档文件，当前有效要求和未决项仍留在恢复入口。日志和录屏按现有目录保存，不全部塞入 JSON。

## 6. 验证与授权

按 [Unity CLI 规则](../04_Standards/Unity_CLI_Development_Rules.md)选择足以证明当前结果的检查。没有哈希门禁、固定修复轮数或强制全量回归。已授权的内部实现和修复直接推进；只确认会改变用户目标、公共行为、所有权或依赖的未决选择。

这是开发记忆协议，不扩大任务范围。涉及外部发送或发布等动作仍按实际用户授权执行，不因为参考模板列出命令就执行。
